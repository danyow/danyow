# 根域名发布与每日任务

2026-09-15：正式网站为 `https://danyow.cn/`。引擎日报每天北京时间09:00开始，电话语音日报09:10开始。两个已有任务分别运行；错开的是启动时间，不承诺发信也精确相差十分钟。

## 单一源码，明确发布目标

- 唯一网站源码、笔记、文档、博客与研究原稿：`danyow/danyow` 的 `main`。
- 根域名发布仓库：`danyow/danyow.github.io`；触发配置在 `master`，网站产物在 `gh-pages`。
- 正式引擎栏目：`https://danyow.cn/ai-engine-watch/`。
- 正式语音栏目：`https://danyow.cn/voice-agent-watch/`。
- 旧 `/danyow/` 项目站暂时保留，仅兼容旧邮件。新通知不使用旧前缀。原稿文件路径、内容、修订号和原稿哈希不因网址变动而改变。

根站通过现有 GitHub Actions 用 `SITE_BASE_URL=/` 构建同一份源码，没有复制正文仓库，没有新增定时任务、Google中转或外部凭据。原项目站的构建结果不能代替根站发布成功。本文件取代早期部署说明中“只检查 danyow/danyow 的 gh-pages 和 /danyow/ 即算完成”的做法；研究范围、写作规范、原稿协议与隐私边界继续保留。

## 日报任务的执行顺序

1. 通过 GitHub 读取根站产物仓库 `gh-pages` 的本栏目 `index/recent.json`，需要时读取月份索引；用源码仓库 main 检查当天原稿，并结合已发邮件去重。初始迁移时允许读旧索引作历史线索，但不当作正式根站发布回执。
2. 只向源码仓库本栏目 `reports/YYYY/MM/YYYY-MM-DD.md` 提交已校验原稿，条件更新，记录真实提交与规范化SHA-256。保留现有JSON元数据、日期、revision和来源规范；不改其他文章或代码。
3. 检查根站对应日期回执及原稿哈希；如果同稿已经在根站发布，无需重复触发。若当前根站运行会包含同一稿，也先复用该运行。
4. 需要发布时，读取 `danyow/danyow.github.io` 的 `master:deployment/source.json` 及其当前blob SHA。此文件只含 `schema=1`、`repository=danyow/danyow`、`branch=main`、`source_sha=真实main提交SHA`。将 source_sha 更新到当前源码 main 上包含该原稿的提交，用当前blob SHA条件更新；只允许写这一发布请求文件，不修改根站工作流、权限、域名或历史。
5. 根站 `Publish root news site` 由这个请求提交触发。工作流读取运行时最新源码 main 并验证包含请求提交，防止并行栏目相互回滚。跟踪根站仓库 master 上匹配请求提交的 push 运行；若当前请求已被更新，须验证后续运行包含本稿才复用，不能用任意绿色勾代替。
6. 同一次任务内约60秒检查必要状态，目标最长20分钟且受运行和工具预算限制。不要首次构建中就结束，不密集取全日志，不擅自新增检查任务。明确失败或审批时停止无效等待；超时保留状态供下一次实际运行恢复。
7. 读取根站 gh-pages 和公开域名本栏目 `receipts/YYYY-MM-DD.json`、日期HTML与raw，日期/revision/sha256相符且网页有 `source-sha256:` 标记。再读根站 `.well-known/danyow-deployment.json` 确认 base 为 `/`、源码来自 danyow/danyow 且包含本稿。构建成功、Pages部署、真正根站页面可访问分别核验。
8. 全部通过后，沿用任务私有Gmail和pushplus收件配置，分别发短摘要和根目录固定日期链接。标题为“栏目名称｜MM-DD”，不带机器前缀；页脚完整日期/修订/哈希标识仍用于防重复。旧邮件和新邮件合并去重；仅网址迁移不触发重发。失败只发简短异常说明，不发送坏链接或伪称完成。

## 维护与权限边界

每日任务新增的唯一写入授权是根站 `master:deployment/source.json`。如该路径不可写，报告发布受阻，不申请额外令牌、不绕过分支保护。根站工作流不需要跨仓库写权限，只公开读取源码并写自身 gh-pages。稿件、私有邮箱、电话、推送token和邮件投递记录不会进入发布请求。

手动改主题或源码后，维护操作也要更新根站发布请求或手动触发该根站工作流；仅主源码仓库构建不会自动刷新根域名。根站通过本文件所述请求触发，无隐藏的跨仓库自动同步。
