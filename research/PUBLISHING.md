# 根域名发布与每日任务

2026-09-15：正式网站为 `https://danyow.cn/`。引擎日报每天北京时间09:00开始，电话语音日报09:10开始。两个已有任务分别运行；错开的是启动时间，不承诺发信也精确相差十分钟。

## 单一源码，明确发布目标

- 唯一网站源码、笔记、文档、博客与研究原稿：`danyow/danyow` 的 `main`。
- 根域名发布仓库：`danyow/danyow.github.io`；触发配置在 `master`，网站产物在 `gh-pages`。
- 正式引擎栏目：`https://danyow.cn/ai-engine-watch/`。
- 正式语音栏目：`https://danyow.cn/voice-agent-watch/`。
- 旧 `/danyow/` 项目站已改为仅自动跳转，不再发布第二套正文或资源；本源码仓库的 `gh-pages` 只存跳转产物，不能用作机器归档索引。新通知不使用旧前缀。原稿文件路径、内容、修订号和原稿哈希不因网址变动而改变。

根站通过现有 GitHub Actions 用 `SITE_BASE_URL=/` 构建同一份源码，没有复制正文仓库，没有新增定时任务、Google中转或外部凭据。项目仓库的工作流仍测试并校验根站构建，但向它自己的Pages只发布轻量跳转页，不再发布完整子路径网站。跳转入口发布成功不等于根站更新成功。本文件取代早期部署说明中“只检查 danyow/danyow 的 gh-pages 和 /danyow/ 即算完成”的做法；研究范围、写作规范、原稿协议与隐私边界继续保留。

## 日报任务的执行顺序

1. 通过 GitHub 读取根站产物仓库 `gh-pages` 的本栏目 `index/recent.json`，需要时读取月份索引；用源码仓库 main 检查当天原稿，并结合已发邮件去重。旧源码仓库 `gh-pages` 已移除正文和索引，历史资料从源码 main、根站索引或Git历史读取，不再尝试依赖旧子路径索引。
2. 只向源码仓库本栏目 `reports/YYYY/MM/YYYY-MM-DD.md` 提交已校验原稿，条件更新，记录真实提交与规范化SHA-256。保留现有JSON元数据、日期、revision和来源规范；不改其他文章或代码。
3. 检查根站对应日期回执及原稿哈希；如果同稿已经在根站发布，无需重复触发。若当前根站运行会包含同一稿，也先复用该运行。
4. 需要发布时，读取 `danyow/danyow.github.io` 的 `master:deployment/source.json` 及其当前blob SHA。此文件只含 `schema=1`、`repository=danyow/danyow`、`branch=main`、`source_sha=真实main提交SHA`。将 source_sha 更新到当前源码 main 上包含该原稿的提交，用当前blob SHA条件更新；只允许写这一发布请求文件，不修改根站工作流、权限、域名或历史。
5. 根站 `Publish root news site` 由这个请求提交触发。工作流读取运行时最新源码 main 并验证包含请求提交，防止并行栏目相互回滚。跟踪根站仓库 master 上匹配请求提交的 push 运行；若当前请求已被更新，须验证后续运行包含本稿才复用，不能用任意绿色勾代替。
6. 同一次任务内约60秒检查必要状态，目标最长20分钟且受运行和工具预算限制。不要首次构建中就结束，不密集取全日志，不擅自新增检查任务。明确失败或审批时停止无效等待；超时保留状态供下一次实际运行恢复。
7. 读取根站 gh-pages 和公开域名本栏目 `receipts/YYYY-MM-DD.json`、日期HTML与raw，日期/revision/sha256相符且网页有 `source-sha256:` 标记。再读根站 `.well-known/danyow-deployment.json` 确认 base 为 `/`、源码来自 danyow/danyow 且包含本稿。构建成功、Pages部署、真正根站页面可访问分别核验。
8. 全部通过后，沿用任务私有Gmail和pushplus收件配置，分别发短摘要和根目录固定日期链接。标题为“栏目名称｜MM-DD”，不带机器前缀；页脚完整日期/修订/哈希标识仍用于防重复。旧邮件和新邮件合并去重；仅网址迁移不触发重发。失败只发简短异常说明，不发送坏链接或伪称完成。

## 故障隔离与恢复

2026-10-04：明确区分以下三条状态，防止将独立镜像故障误判为正式日报发布失败。本节仅澄清现有协议，不扩大每日任务权限。

**正式根站**：只以匹配请求提交的 `Publish root news site`、对应 Pages 发布，以及 `https://danyow.cn/` 的公开日期页、raw、日期回执和部署标识判断发布。源码、修订和哈希校验仍必须全部通过。工具访问受限时写“本次无法公开核验”，不能把它说成网站宕机，也不能用历史成功或仅仓库产物代替本次验收。

**独立 Vercel 镜像**：`Validate Vercel mirror build`、`Verify public Vercel production` 和提交状态 `Vercel` 不是根站发布工作流。`VERCEL_RECEIPT_MISMATCH` 表示镜像部署回执的某项检查失败，不自动说明日报原稿错误、根站未发布或 Gmail 失败。根站已按上文完整核验时，镜像故障不得阻断正常邮件；保留镜像错误供单独维护，不关闭或放宽它的校验来伪造成功。镜像回执当前使用顶层 `request_commit` 和 `source_commit`，不是 `vercel.request_commit`。

**工具与投递**：GitHub、Gmail 每次分别确认能力与真实结果。HTTP鉴权错误、冲突、限流、参数错误与工具安全拒绝分开记录，错误码和最小必要原因只留私有运行记录。不能仅凭“允许所有操作”或读取成功认定写入成功，也不能把没有原始错误的历史概述升级成已查明的拒绝原因。安全拒绝停止对应操作，不换通道规避；状态不明先回读或查 SENT，不盲重发。正式邮件仍只在根站全部验收后发送，且按每个收件人独立去重。

单次失败或连续失败都不授权修改每日任务的启用状态、调度、通知设置或收件人。保留可恢复进度；未经用户明确要求不得暂停、删除、另建或改名，也不得为修复工具错误增加令牌或扩大权限。

## 旧地址跳转边界

旧地址按路径映射到根目录同一篇文章，保留查询参数及片段。项目Pages的自定义404处理尚无独立跳转文件的旧路径；不能把不带 `/danyow/` 的新地址再次跳转。已知页面设置根地址canonical和noindex，且有无脚本回退；不承诺搜索引擎的收录行为。

此实现是静态页面中的 `location.replace`，不是HTTP 301/308，HTTP抓取器和旧API调用方必须改用根站地址。没有修改DNS或Cloudflare配置，没有保留两份文章正文。后续需要真正HTTP永久重定向时，应在有授权的代理/边缘层配置精确的旧前缀规则，不能把静态页的200/404描述成301。

## 维护与权限边界

每日任务新增的唯一写入授权是根站 `master:deployment/source.json`。如该路径不可写，报告发布受阻，不申请额外令牌、不绕过分支保护。根站工作流不需要跨仓库写权限，只公开读取源码并写自身 gh-pages。稿件、私有邮箱、电话、推送token和邮件投递记录不会进入发布请求。

手动改主题或源码后，维护操作也要更新根站发布请求或手动触发该根站工作流；仅主源码仓库构建不会自动刷新根域名。根站通过本文件所述请求触发，无隐藏的跨仓库自动同步。
