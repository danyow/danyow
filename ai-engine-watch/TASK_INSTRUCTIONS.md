实际联网检索全球 AI-native game engine、agent-first 引擎、神经游戏引擎、交互世界模型、相关论文、代码、模型权重、实验与可玩 Demo，持续发现新项目。

研究覆盖项目具体进展、用途、可用程度、论文或代码的贡献和局限、原始入口，以及对其他AI原生引擎、传统引擎和游戏开发者的影响。把这些要点合并到少量重点条目里，不按栏目重复分析同一项目。每条实质信息附原始来源；区分事件发生、报道发表、本次发现日期。事实、项目方主张、分析与未验证信息分开；无重大新增仍报告，检索失败不能当作没有新闻。

## 读者看到的格式

网页正文通常500至800个中文字，通常不超过1000字；确有多条重要进展时最多1200字。字数不含JSON元数据、链接地址及系统版本页脚。这是目标和上限，不是最低字数，不凑篇幅。没有重大新增时80至150字即可。

邮件正文约100至150字，最多3条口语摘要，加当天阅读链接和归档入口。归档首页也使用这些短摘要。任务完成说明最多2句，不再复述整套工作流程。

### 网页结构

正文以“AI 引擎日报｜YYYY-MM-DD”为一级标题，随后依次为：

- **今天一句话**：30至50字，最多2句，先说最重要的判断，不写开场套话。
- **今天值得看**：通常1至3条重点，新闻确实多时最多5条。论文、仓库和引擎按价值混排，不为类别凑条目。
- **顺手看**：可选，最多3条，每条20至40字加来源，只放前面没讲过的有价值发现。
- **我的看法**：可选，最多2句且合计不超过60字，只写跨项目的新判断，不重复上文用途。

每条重点标题使用“项目名：一句话说清新变化”，必要时注明论文、开源项目或引擎，不照搬完整英文论文标题。内容用3个短句或3行，合计约80至130字：

**新在哪：** 这次具体做了什么。必要的项目背景只补半句。

**有什么用：** 能帮游戏开发者省什么事，或对现有引擎有什么实际影响。推测用“可能”“我的判断”。

**现在能用吗：** 可下载、可试用、只放演示、只有论文等实际状态，加最重要的限制。

每条最后独立一行放通常1至3个支持该条的原始入口，链接名称采用“论文 · 日期”“代码 · 日期”“演示”等。关键依据不可为了省字而删除，需要更多来源时可以增加。日期不明写未注明，不能附错日期。

正常检索只在末尾用一行说明观察窗口；关键来源打不开、去重受限时用一句直白说明。元数据保留发生、发表、发现三个日期，正文只强调影响新旧判断的差异，例如“上周发布，今天补录”。周日可加不超过100字的周度变化，不新增推送。

### 语言和排版

面向懂游戏开发、但不必懂论文算法的读者。先讲做了什么、有什么用、目前还差什么。使用短句和常用词，保留项目名，减少专业缩写；必要术语首次出现紧接一句很短的白话解释。技术细节留在原始入口，不把论文摘要逐句翻译成长段说明。

不用“范式重构”“赋能生态”等空话，不连续堆专业词。关键数字只保留影响判断的一两项并说明测试条件。自然表达证据边界，例如“作者说有提升，还没看到独立测试”“代码还没放出来”“这里只是我的判断”，不在每句话前重复长标签。口语化不能把猜测写成事实，也不能把演示写成可以直接做完整游戏。

每段1至2句，最多三级标题，适量加粗。避免宽表格、长编号、嵌套清单、公式和整段代码，不使用HTML折叠或JSX。同一事件不要在今日重点、研发进展、论文分析、行业影响中反复讲几遍。

机器字段、完整哈希、提交SHA及运行ID不展开到正文，只保存在元数据、回执或必要的系统页脚。

### 正文骨架

以下仅为格式骨架，不是实际资讯，不提交到reports：

```markdown
# AI 引擎日报｜YYYY-MM-DD

**今天一句话：** 最重要的变化和一句判断。

## 今天值得看

### 项目名：一句话说明新变化

**新在哪：** 一句说清这次新增的能力或研究结果。

**有什么用：** 一句说明具体用途或可能影响。

**现在能用吗：** 一句说清开放状态和主要限制。

来源：使用真实的论文、代码或演示链接，并标注已核实日期。
```

## Markdown 协议

原稿存入 danyow/danyow 的 main 分支：ai-engine-watch/reports/YYYY/MM/YYYY-MM-DD.md。使用 examples/report.md 的 JSON front matter：独立 --- 行、完整 JSON、独立 --- 行，随后是以一级标题开始的 Markdown 正文。

只允许且必须包含 schema/date/timezone/title/revision/publication/review_status/summary/events。schema=1；timezone=Asia/Shanghai；date使用报告北京时间日期；首次revision=1，更正递增；可公开稿publication=publish；自动生成review_status=generated，不冒充人工reviewed，不提交hold或imported-unverified。

新稿summary采用1至3条口语短句，每条最多45个中文字，供首页及邮件直接使用。这是写作约定，不修改现有schema的1至5条、每条280字符兼容上限。events最多40项，每项仅含project/title/kind/event_date/publication_date/discovered_date/evidence/source。project为不超过80字符的小写字母、数字、连字符标识；事件标题最多180字符，优先用简短白话。kind取release/paper/code/demo/funding/industry/correction/other；evidence取verified/source-claim/analysis/unverified。未知发生/发表日期使用null，发现日期不得晚于日报日期，来源使用无凭据的真实HTTP(S)链接。无可收录事件时events=[]。

全文UTF-8、无BOM、LF换行、首尾去空白后加一个末尾换行，不超过120000字节。纯Markdown，不含HTML/JSX、脚本、import/export、邮件头、邮箱、Webhook、token或私人配置。用程序校验格式并计算规范化全文SHA-256；共享解析规则位于bridge/Core.gs。

## 直接提交

实际发现并调用当前任务可用的GitHub工具。先读取当天文件及其当前blob SHA：不存在则创建；完全相同则不重复提交；必要更正增加revision、注明原因，用当前SHA条件更新，不覆盖并发变化。日常仅操作reports目录，不改工作流、站点、权限或其他文章，不删除历史、不强推。

写入后回读确认，记录实际提交SHA。不要由模型另写HTML或提交生成副本，交给现有Actions。写权限不足、审批或分支保护阻止时明确失败，不绕过。

## 同一次任务内检查，直到发布验证通过

上传后立即进入等待阶段，不能因为第一次查询仍是构建中就提前发日报。保留原稿日期、revision、sha256、commit SHA、相应workflow run ID和等待开始时间。

1. 查找main分支、本次提交触发的push构建。使用可筛选branch/event/head_sha的查询；某些名为fetch_commit_workflow_runs的封装只返回PR运行，不适合据此判断main的push构建是否存在。必要时通过已授权GitHub工具读取actions/runs或工作流运行集合，再按head_sha核对。
2. 构建或部署仍queued/in_progress/pending时，在本次执行内间隔约60秒继续检查。只读取必要状态摘要，不反复下载完整日志和日报；限流遵守Retry-After，查询失败不自动等于构建失败。不得创建每分钟重复执行的第二个定时任务。
3. completed不代表成功，构建和部署的结论必须为success。明确failure/timed_out/action_required等状态时检查失败步骤或审批需求，不能对已失败运行无休止等待。cancelled时可检查是否有包含同一原稿的后续提交接替，但必须验证原稿哈希一致，不擅自改代码或无限重跑。
4. 还需确认对应GitHub Pages部署，并读取gh-pages的ai-engine-watch/receipts/YYYY-MM-DD.json。date、revision、sha256必须匹配当前MD，不能把历史成功记录当本次成功。
5. 实际请求公开回执、当天固定网页及必要的raw原稿。页面须正常返回、不是错误页或登录页，并包含source-sha256:<当前原稿哈希>；公开回执的日期、修订号和哈希也须一致。HTTP 200本身不能证明正文是最新版本。
6. 所有条件成立后才发正式摘要和固定阅读链接。未完成前不向邮件/pushplus发送日报全文、阶段性摘要、半成品网页或成功通知。

等待阶段目标最多20分钟，从提交后开始等待算起。这是防卡死的工作流策略，不是平台保证的单次运行时长；如本次执行预算更早耗尽、工具不可用或需要审批，则停止并报告。遵守各工具自身超时，不伪造等待，不无限轮询，也不声称任务结束后会凭提示词继续后台执行。

## 成功后发送

Gmail分别向私有任务配置中的本人邮箱和已验证pushplus邮箱独立发送，两端主题一致：`AI 原生游戏引擎每日观察｜MM-DD`，例如 `AI 原生游戏引擎每日观察｜09-12`。标题在前，月日补零的短日期在最后，不加机器前缀、不显示年份。日期取本份报告的北京时间日期，而不是补发当天。修订、补发和异常状态放在标题后的括号中、日期之前，例如 `AI 原生游戏引擎每日观察（补发）｜09-12`。

读者正文100至150字左右，直接用summary的1至3条口语短句，加“阅读今天日报”“历史归档”两个已验证链接，不追加重复总结、操作步骤或长篇技术说明。无重大新增时一句说明加链接即可。原稿哈希与AIENGINE-YYYY-MM-DD-rN标识放末尾一行低强调版本信息，不解释技术含义。允许极简HTML包装链接，不发送整篇HTML，不只创建草稿。

短日期只用于邮件标题。原稿元数据、文件名、网页链接、索引、回执和页脚去重标识仍使用完整YYYY-MM-DD。发送前按完整日期、修订、原稿哈希、收件人和标识查已发送记录，同时兼容新主题及旧[AIENGINE-DAILY]主题，不能只按标题、旧前缀或月日去重；异常通知不算正式投递。只补未成功的一端；状态不明先查证，不盲目重复。仅改变标题样式不重发旧邮件，也不修改历史原稿。Gmail成功仅记邮件发出，不当作手机最终送达。

## 失败、超时和恢复

写入、构建、部署或网页核验未完成时，不发送正式日报或未验证的阅读链接，也不回退成整篇正文推送。Gmail可用且授权允许时，只向各收件人发一次主题为`AI 原生游戏引擎每日观察（发布未完成）｜MM-DD`的简短异常说明，用1至2句且最多100字说清卡在哪、原稿是否已保存，不夹带日志和日报正文；版本信息放页脚。按完整日期、revision、原因类别和收件人去重，旧[AIENGINE-PIPELINE]仅用于历史异常识别，不用于新主题。隐私校验失败只告知本人，不把可疑原稿发往推送平台或公开仓库。

已入库MD留在仓库，未入库MD留在私有任务结果。执行记录保留日期、revision、sha256、提交、运行ID、已完成步骤及发信结果作为恢复依据；个人投递记录不能写进公开仓库。面向用户的完成说明最多2句，说明发布和邮件状态；失败时只点出卡点和已保留内容。

下一次实际运行从仓库、回执、Gmail记录重建进度，复用原稿继续检查，成功后补发，不重写同稿或重复发送。优先恢复近7天最近一份未完成原稿，同时处理当天报告，不批量补发。当前只有每日调度，不能把下次恢复描述成超时后会立即自动续跑。
